The LatticeWire protocol

How LatticeWire builds a quantum-safe tunnel in one round trip, moves data at line rate, and disguises itself as web traffic. Version 3 of the protocol.

Abstract

LatticeWire is a point-to-site VPN whose handshake combines classical X25519 with ML-KEM-768 and authenticates the server with ML-DSA-65, so that traffic recorded today stays private even against an attacker who later builds a quantum computer. The handshake takes one round trip and follows the Noise IK pattern. Data is sealed with AES-256-GCM or XChaCha20-Poly1305 and carried over a batched UDP data path. An optional stealth layer makes the tunnel look like an HTTP/3 connection to a real website, with a TLS-over-TCP fallback for networks that block UDP.

Design goals

  • Quantum-safe confidentiality. Session keys depend on both a classical and a post-quantum secret; recovering one is not enough.
  • Strong server authentication. The server signs the entire handshake transcript with a post-quantum signature.
  • One round trip. Two messages, then data, with no extra exchange for cipher negotiation.
  • Line-rate data path. Per-packet work small enough to beat established tunnels on the same hardware.
  • Censorship resistance. An optional encoding that matches real QUIC and TLS on the wire.
  • Operability. Server-assigned addresses, IPv4 and IPv6, roaming and automatic recovery.

The handshake

LatticeWire extends the Noise IK pattern. The client already knows the server's static X25519 key and ML-DSA-65 verification key from its configuration.

ClientHello

The client sends a fresh ephemeral X25519 key and a random nonce, then two sealed blocks. Its static public key is encrypted under a key derived from es, the ephemeral-static agreement, so only the real server learns which client is connecting. The second block carries a fresh ML-KEM-768 public key, a millisecond timestamp and a capability byte. It is sealed under a key derived from both es and ss, the static-static agreement, which only the holder of the client's private key can compute. Opening it therefore proves the client's identity in the first message.

ServerHello

The server checks freshness, encapsulates to the client's ML-KEM key, assigns the tunnel addresses, chooses the cipher and signs the transcript with ML-DSA-65 under a dedicated context string. The reply is sealed under a key derived from ee. The transcript covers the ClientHello bytes, the server's ephemeral key, the KEM ciphertext, both assigned addresses and the cipher choice, so none of them can be altered in flight.

Freshness

A hello is accepted only if its authenticated timestamp is within three minutes of the server's clock and newer than the last one from that client. An identical retransmission from the same address receives the cached reply, up to eight times, so packet loss never costs a second key exchange.

Cipher negotiation

The client sets an offer bit when its CPU accelerates AES. The server chooses AES-256-GCM only if both sides have the hardware and policy allows it, and otherwise XChaCha20-Poly1305. Because the choice is inside the signed transcript, it cannot be downgraded, and a client rejects a choice it did not offer.

Key schedule

All secrets are mixed in one BLAKE3 derivation, then split into one key per direction.

transcript = H("transcript", ClientHello ‖ e_s ‖ kem_ct ‖ ipv4 ‖ ipv6 ‖ cipher)
session = KDF("session-key", ee ‖ ss ‖ kem_ss ‖ es ‖ transcript)
k_i, k_r = KDF("initiator", session), KDF("responder", session)

For XChaCha20-Poly1305, each direction's 24-byte nonce is a fixed 16-byte prefix derived from its key followed by the 8-byte packet counter. LatticeWire computes the HChaCha20 subkey once per session and seals each packet with ChaCha20-Poly1305 under the nonce 0⁴ ‖ counter, which is byte-for-byte the XChaCha construction. For AES-256-GCM, each direction uses a separately derived key with the same counter nonce.

Admission and floods

Every ClientHello ends with mac1, keyed by the server's public key, and mac2. The server verifies mac1 with one hash before any public-key work, so random traffic costs almost nothing. Above 1,000 valid hellos per second the server is under load: it then requires a valid mac2, keyed by a cookie bound to the sender's address, and answers everything else with a 57-byte cookie reply. The cookie secret rotates every two minutes, and proven senders get a per-address budget. A forged flood never sees a cookie, so it can't push the server into expensive work.

Data transport

Each data packet is [type 1][counter 8][ciphertext][tag 16], with the counter as associated data. Counters are reserved in queue order, so packets of a flow leave in the order they were sealed. On receive, packets are decrypted and then checked against a 4,096-packet anti-replay window (RFC 6479 ring bitmap, constant time per packet) exactly once, in arrival order. A duplicate can never be accepted twice, even if two copies are decrypted at the same moment.

Session lifecycle

  • Rekey every 15 minutes with up to three minutes of jitter, or after 232 packets, whichever comes first.
  • Hard limits at 45 minutes or 248 packets, after which a key is never used again.
  • No gaps. The server holds new keys as pending and promotes them on the first valid packet, and the previous keys keep decrypting late packets for 30 seconds. A lost ServerHello never interrupts traffic.
  • Liveness. Keepalives every 15 seconds; a client marks the link stale after 20 seconds of silence and reconnects on a fresh socket after 25.

Data-path engineering

On Linux the TUN device runs with virtio headers, so the kernel hands LatticeWire whole TCP super-segments. They are split, sealed and sent with UDP GSO, many datagrams per system call. On receive, UDP GRO delivers batches. After decryption, consecutive segments of each TCP flow are merged back into one large frame, with checksums verified first, so the kernel's TCP stack runs once per 64 KB instead of once per packet.

Workers cache the current keys and only take a lock after a rekey, time checks read a shared millisecond clock, and decrypted batches go to a dedicated TUN writer so decryption and kernel work overlap.

Addressing and roaming

The server assigns each client an IPv4 tunnel address and, when a prefix is configured, an IPv6 address built from the prefix with the IPv4 address in its low 32 bits. Both are signed in the ServerHello. The server checks that every decrypted packet carries the client's own source address. Roaming is handled by the handshake itself: a fresh authenticated hello from a new address moves the session.

Stealth layer

In Phantom mode a client opens with a genuine QUIC Initial carrying a browser-style TLS ClientHello for the configured site. Its destination connection ID carries a MAC under the client's stealth key, so the server recognises it while anyone else sees a random ID. The server answers with a QUIC server flight shaped like a real one, within the three-times anti-amplification limit, and the tunnel then continues in QUIC short-header packets addressed to the connection IDs chosen in that exchange.

In Ghost mode the server forwards the client's Initial unchanged to a real web server and relays the genuine reply, so the opening is the site's real handshake, certificate included.

Every tunnel packet's type and counter are masked with a keystream derived from a sample of the ciphertext. Connection IDs are random, and the server recognises them through a table of the IDs it issued. Each client may have its own stealth key, random padding hides packet sizes, idle periods carry cover traffic, and clients move to a fresh cover connection roughly every half hour.

TLS fallback

When UDP gets no answer, a client opens TLS 1.3 to port 443 and sends a 40-byte token: a random nonce, a timestamp and a MAC under its stealth key. Each nonce is accepted once. The stream then carries length-prefixed datagrams into the normal data path through a loopback socket. Any connection without a valid token is handed to the operator's real website, so probers see an ordinary HTTPS site.

Implementation

LatticeWire is written in Rust on the Tokio runtime. It uses ring's assembly AES-GCM and ChaCha20-Poly1305, Cryspen's libcrux implementations of ML-KEM and ML-DSA, and x25519-dalek. The test suite has 98 unit and integration tests, including RFC test vectors for the QUIC key schedule and byte-for-byte checks against reference XChaCha20-Poly1305, and 41 end-to-end checks that run real tunnels in Docker.

Future work

  • KEM-based server authentication in place of the signature, halving the handshake size.
  • Post-quantum client authentication.
  • Variable-length connection IDs for Ghost mask servers.
  • An independent audit of the protocol and implementation.
